# Code audit: Hearthbrew core, content, UI and art layers (2026-10-12)

> **Status (2026-10-13):** **All 7 directions are done** (see `design/content-model.md`, `design/effects.md`, `design/ui-architecture.md`, the pack structure in `design/visual/05-design-system.md`, and "Where rules live" in `design/brew-math.md`), and the Python tools are frozen as historical validation. **Found while closing Direction 7:** CI's type check had failed on every push since `4b7c903` (11 strict-JSDoc errors, no runtime bugs). It now runs locally (`npm run typecheck`), the errors are fixed, and checking CI after each push is part of the workflow. **Still open:** `morph` is covered by browser checks only (there's no DOM in Node, by design). **Deferred:** a statistical balance bot-play over many seeds, to run once the game flow is defined (the user's decision).

## Context
- **What was asked:** an independent review of the code written so far, judging how well it can absorb new features and new content. It was reviewed as if another developer wrote it. No changes were made during the audit.
- **Scope:** about 1,340 lines of game code (`src/core`, `src/content`, `src/ui`, `src/sim`, `src/art/registry.js` + `geom.js`), plus about 170 KB of art packs (`src/art/styles/*`), the tests and the tooling.
- **Method:** read every file, then trace what it would cost to add 8 typical future extensions.

## Overall verdict
**A solid prototype-grade foundation that is not yet a content platform.**
- **The engine works:** the rules are pure functions, randomness is seeded and reproducible, there's one content file, art goes through a registry, colours through tokens, and parity tests check the port against the Python reference.
- **What won't scale is the extensions:** behaviour is selected by `if/else` chains and hard-coded ids instead of data or registries. That keeps today's code short, but every new card, event, rule or customer touches **3–5 files across layers**.
- **The UI rebuilds whole screens from strings on every tap.** That's fine for 5 screens, but it will hurt with brewing, the Notebook and animation.

| Area | Score (1–5) | One-line reason |
|---|---|---|
| Core rules (`brew`, `score`, `haul`, `rng`) | **4** | Pure, tested, deterministic. Rules are hard-coded, but there are few of them |
| Day loop (`day.js`, `state.js`) | **3** | Correct and tested, but card and event behaviour is an `if/else` per type, and the phases are an implicit state machine |
| Content model (`content.json` + `index.js`) | **2.5** | One file (good), but two parallel herb catalogues, no validation, ids and strings hard-coded in code |
| Saves | **4** | Versioned with migrations and tests. No protection against renamed content ids |
| UI layer (`game.js`, `screens/`) | **2.5** | Readable, but full re-render via `innerHTML`, focus is lost on every tap, and screen wiring is copy-pasted |
| Design system (`tokens.css`, `components.css`, lint) | **4** | A clean semantic layer enforced by a test. Components will need splitting as they grow |
| Art system (`registry`, packs, LOD) | **3** | The swappable registry is a strong idea, but the packs are large single files, all of them load at start, and LOD works by regex over SVG text |
| Tests and tooling | **3.5** | Strong core coverage and a 20-day bot; no UI tests, and the type check runs only in CI |

## Extension cost (at audit time)
| Future addition | Files touched | Main friction |
|---|---|---|
| New ingredient (e.g. *yarrow*) | `content.json` ×2 sections (`ingredients` + `haul.herbs`), each art pack, maybe `brew.js` | **Two catalogues must agree by hand** |
| New morning card (e.g. *Fishing*) | `content.json`, `state.js` (the `CardType` union), `day.js` (a new branch), `morning.js` (the `cardArt` map) | Behaviour lives in a `chooseCard` if/else |
| New event type (e.g. *Wisp chase*) | `content.json`, `state.js`, `day.js` ×2 (draw + resolve), `event.js` (new markup) | The kinds are hard-coded in both the draw and the resolve |
| New customer | `content.json`, `state.js` (the **hard-coded `relationships` list**), an art portrait | `relationships` started as `{marla, pell, fennick, bramble}`: **`tamsin` was missing and `bramble` isn't a customer** |
| New brewing rule (R9) | `brew.js` (inline code), the `RuleId` type, Python reference + fixtures | Order-dependent inline logic; `honey` and `water` were named in code |
| New weather | `content.json` + art | ✅ **Data-driven already.** The model to copy |
| New style pack | `styles/<id>/` + one import in `registry.js` | ✅ Contained; only the registry import is manual |
| Translation | most UI files + `day.js` | **UI text spread across code**; trait names defined 3 times |

## Findings
### A. Content model (addressed by Direction 1)
1. **Two sources of truth for herbs.** `content.ingredients` and `content.haul.herbs` described the same plants separately. → One entity per herb with a `forage` facet.
2. **No content validation.** A typo failed only when that code path ran. → `validateContent()`.
3. **Ids and constants in code:** `START_STOCK`, the initial `relationships` (buggy), `'water'` and `'honey'` in `brew.js`, `20` days, the card-art map. → The `start` section, card `art`, the default base, the `sweetener` tag.
4. **UI and story text in code;** trait names ×3. → The `strings` table and `t()`.

### B. Core and state
5. **Behaviour by `if/else` per type** (`chooseCard`, the event draw, `resolveEvent`). Alternatives:
   - **(a)** a handler registry;
   - **(b)** data-driven effects from a small vocabulary (`addItems`, `coins`, `friend`, `learnHerb`, `learnRule`);
   - **(c)** both. **Recommended: (c).**
6. **An implicit state machine.** The phases live in strings, guards are scattered `throw`s, and `runShop` → `endDay` are chained in the UI. → An explicit transition table plus `dispatch(state, action)`.
7. **Unclear data semantics:** `notebook.known` is `boolean[]` per trait but always all-true; `today` mixes generated data with progress and results. Settle before the Notebook screens.
8. **Determinism is good but fragile:** the `rngFor` salts are hand-numbered. → Named streams.
9. **Save robustness:** content-id drift wasn't handled. → Aliases plus load-time repair (**done in Direction 1**).
10. **Layering leak:** `ui/game.js` imports `sim/haulSim.js` for the debug bot. → A lazy `import()`.

### C. UI layer
11. **Full re-render on every interaction:** focus and screen-reader position reset, scroll needs restoring, no element-level animation. → A vendored lit-html/uhtml (no-build ESM) is the most future-proof.
12. **No HTML escaping** in templates. → An `esc()` helper or a templating library.
13. **The screen pattern is copy-pasted,** and the router is a ternary chain. → A screen registry plus a shared `mount()`.
14. **Long-press is the only path to details.** → A visible details affordance too.

### D. Art system
15. **The LOD mini pass is a regex over SVG strings.** → LOD-aware drawing primitives.
16. **Every pack is imported at start-up** (about 170 KB). → A manifest plus dynamic `import()`.
17. **The packs are monoliths.** → Split by asset family, with shared primitives.
18. **Behaviour CSS in pack CSS** (`.nb-sketch` develop rules). → Move it to `components.css`.

### E. Tests and tooling
19. **Strengths:** parity fixtures, balance sims as tests, the 20-day bot, the CSS lint, the art defs and LOD tests.
20. **Gaps:** no screen-output tests, no content-validation test (**added**), the type check runs only in CI.
21. **Dual Python/JS maintenance.** **Decided 2026-10-13:** Python is frozen as historical validation; the JS core is the source of truth.
